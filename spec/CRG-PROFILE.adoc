== About this profile

This profile applies the *CRG v2.2 (STRICT)* baseline to My
released components. No My crate is yet published to crates.io;
the `my` binary (via `my-cli`) is the primary released artefact,
plus the 13 workspace crates that consumers could pull as git
dependencies.

CRG = *D*. The full chain of axes:

* ARG: *D-leaning-E* (per `spec/ARG-PROFILE.adoc`)
* TRG: *D* (per `spec/TRG-PROFILE.adoc`)
* FRG: *X* (per `spec/FRG-PROFILE.adoc`)
* CRG: *D* (this profile)
* RSR: Compliant at TRG-D level

== Per-component evidence (deep)

CRG §4.5+ (grade C onward) requires *deep per-file + per-directory
annotation*. The current state has no `audits/audit-<crate>.md`
files. Three relevant existing documents:

* `docs/wiki/reference/stdlib.md` — covers `my-lang::stdlib`
  released surface
* `docs/wiki/internals/stdlib-design.md` — design rationale for the
  stdlib module
* `PROOF-NEEDS.md` — records the 2026-03-29 retraction of the
  template ABI scaffolding

These are good documentation but do not meet the v2.2 STRICT per-
component audit clause.

== Language-specific tightening (this profile only)

For My, the following additional CRG obligations apply at the
stated grades:

* *Grade C tightening:* The `my-lang::stdlib` (1931 lines) MUST
  have a per-module audit document covering the released symbol
  surface, mirroring the rigour expected of `docs/wiki/reference/
  stdlib.md` at audit level.
* *Grade B tightening:* `my-lang` MUST be published as v1.0 to
  crates.io with at least one external consumer not maintained by
  the My team.
* *Grade A tightening:* Registered VeriSimDB instance + public
  health check + third-party-maintained My library or application.

These tightenings are *additional* to the baseline — none of the
baseline evidence is waived.

== What is NOT yet met (honest gaps)

* *No crates.io publication*. Every workspace crate is internal.
* *No per-component v2.2 STRICT audits* under `audits/`.
* *No VeriSimDB attestation*.
* *Test matrix not yet explicitly documented* — gates the C3
  deep-annotation clause.
* *No external consumers* beyond first-party tooling.

== Path to next grade (*C*)

* Publish at least `my-lang` (the compiler core crate) to crates.io
  as v0.2.0. (~1-2 weeks if API is stable enough)
* Author per-crate audit documents under `audits/`. (~3-4 weeks)
* Land VeriSimDB attestation. (~1 week)
* Document the explicit test matrix (which tests cover which
  invariants for which dialect). (~1-2 weeks)

*Realistic timeline estimate:* 2-3 months from current state.

== Path to grade beyond that (*B*)

* Publish v1.0 of at least one workspace crate.
* External consumer not maintained by the My team.
* Issue-feedback pipeline with external reporters.

== Demotion risk

* *Lowest:* `tests/integration_test.rs` or `tests/property_tests.rs`
  regress significantly.
* *Medium:* The `crates/my-llvm` build path breaks for the primary
  x86_64-linux target (inkwell or LLVM API drift).
* *Catastrophic:* A consumer of an unpublished but consumed crate
  is broken and the breakage is not rolled back.
